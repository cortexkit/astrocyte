# spend-multiplier-report-v1

Synthetic `spend.multiplier.report` reply bodies for desktop decoders. Each file
is the successful response body, `{"result":{"latest":[...],"series":[...]}}`,
generated by `ops::dispatch` against an isolated, migrated synthetic store.
The test seeds plan history, quota readings and usage, computes observations
with the existing estimator, and appends them with the real observation writer.
Account identifiers, plan keys, model names and amounts are invented; no real
store, account, email or spend is used. The seeded observations are report
fixtures, not evidence of any provider's actual calibration or tariff.

| File | Contract case |
|---|---|
| `quota-unestablished.json` | Both `latest` and `series` retain an ineligible pool with a null quota multiplier and explicit eligibility reasons |
| `low-resolution.json` | A low-burn pool has `low_resolution: true`, a numeric descriptive ratio, and `insufficient_points` prohibits routing |
| `routing-eligible.json` | A normal per-plan head has a positive quota multiplier, routing eligibility, model valuation and stability diagnostics |
| `narrow-range.json` | A one-millisecond range includes the earlier day's head at its lower bound and excludes the newer head; `latest` remains unchanged |

The first three requests use `{"from_ms":0,"to_ms":777600001}`. Each store
contains two trailing seven-day observations ending at `691200000` and
`777600000` milliseconds since the epoch (1970-01-09 and 1970-01-10 UTC).
The narrow request uses `{"from_ms":691200000,"to_ms":691200001}` against
the routing-eligible store. `series` selects interval ends in `[from_ms,to_ms)`;
`latest` is independent of the requested range. Daily trailing intervals
overlap, so the rows must not be added to reconstruct consumption.

The unestablished case uses the `claude` provider identifier with deliberately
widely separated readings: no account-hour has bounded quota coverage, so
`multiplier` is null and `insufficient_clean_hours` explains why. Its ancillary
`fee_multiplier` is still numeric; it is not the quota routing divisor. This
is a synthetic example of unavailable quota calibration, not a claim about
the current production state of Claude. The other cases have fifteen-minute
readings; the low-resolution case accumulates too few points, whereas the
eligible plan has seven active days of stable matched value and quota points.

`multiplier_report_vectors_pin_real_dispatch_and_checksums` checks every reply
byte, the SHA-256 manifest, the cases' semantics, and that serving the reports
does not write the store. A reply member addition, removal or type change
therefore requires reviewing and versioning the decoder fixtures.

To regenerate on the build server, run:

```sh
ASTROCYTE_EXPORT_MULTIPLIER_REPORT_VECTORS=1 cargo test --workspace --locked multiplier_report_vectors -- --nocapture
```

Export mode writes the bodies and `SHA256SUMS` into this directory. If the
checkout is read-only, it also prints `VECTOR <filename> <JSON string>` lines
containing the exact file contents, including their final newline. Decode the
JSON string and write those bytes locally, then run the test again without the
environment variable to verify the pinned files. `SHA256SUMS` covers every JSON
body and this README, not itself. Published version tags must not move; changed
published fixtures require a new version and tag.

These files were exported on the Linux build server and copied back with the
build tool's `return_paths`; the read-only-checkout fallback was not needed.
